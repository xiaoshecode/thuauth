# thuauth 实施与协作

本计划把开发分为可独立验收的阶段，并用有限数量的子 agent 处理互不冲突的工作。架构见 [architecture.md](architecture.md)，实际进度与检查结果见 [HANDOFF.md](../HANDOFF.md)。M0 已建立包、配置与本地 CLI；接下来实施 M1 协议。

## 实现前的架构评审

以下结论来自 M0 实现前的两个只读子 agent，分别审查协议移植和运行时故障路径，由主会话结合源码整合。该次架构评审没有执行程序；M0 现已实现并运行 Python 检查，实际结果见 HANDOFF.md。

| 发现 | 依据或触发条件 | 设计处理 |
| --- | --- | --- |
| 无条件双登录可能重复 | GoAuthing `libauth/requests.go:34` 带 double_stack；CLI 一次只选一个 host | 逐栈检查、串行补齐、操作后复查；联动行为校内实测 |
| 原状态解析不支持 IPv6 文本 | `libauth/requests.go:135` 仅接受数字和点 | 新解析与 ipaddress 验证；解析失败为 UNKNOWN |
| 原测试不足以覆盖报文 | `libauth/requests_test.go` 的登录参数测试已注释 | 增加 JSON、MD5、info、checksum 与登出参数对拍 |
| ac_id 与 IP 不能猜测 | `libauth/requests.go:178` 依 V6 选择发现网址；challenge 未采用返回 IP | 分离来源与有效值，发现失败显式处理，绑定规则待测 |
| TaskGroup 正常退出不会终止循环 | 长期运行任务仍在等待 | 显式取消并等待，清理后传播取消异常 |
| 节流可被误判为读取超时 | 慢配额、多 worker、后台预读 | 独立请求类型超时策略，以慢服务器测试验证 |
| 并发和预读影响流量口径 | 每 worker 各自限速、压缩、网络缓冲 | 全局正文预算，声明有限突发与网卡计量差异 |
| 多进程造成认证与登出竞争 | 同账号不同配置启动 keep/logout | 固定用户级锁覆盖所有有副作用入口 |
| debug 可泄露认证材料 | 原 `GetJSON` 打印完整 GET URL | 结构化日志和异常边界脱敏，验证不含测试凭据 |

未采用：全局 DNS monkey patch、吞掉所有异常以维持进程、硬性 700 行限制、任意滚动窗口精确网卡限速，以及为每条意见再派一个验证 agent。它们或增加维护风险，或超出当前需求。认证协议只保持兼容，不把原实现的错误处理一起复制。

## 实施顺序

| 阶段 | 交付 | 完成标准 |
| --- | --- | --- |
| M0 工程与契约（已完成） | pyproject、锁文件、模型、配置、异常、测试入口 | CLI help/init/config check 可用；配置失败与原子写入测试通过 |
| M1 协议 | coding、srun、合成 fixtures | Go 向量、登录登出参数、JSONP、错误响应测试通过 |
| M2 认证客户端 | HTTP 会话、AuthService、login/logout/status/doctor | 本地假服务器通过双栈、超时、账号冲突等测试；无需真实密码 |
| M3 保活流量 | daemon、traffic、limiter、统计与退出 | 本地持续流测试、速率预算、恢复、取消、进程锁通过 |
| M4 集成与交付 | README 使用说明、CI、许可与来源说明 | 静态检查和完整测试通过；列出校内实测步骤与待测项 |

不要以“700 行”作为完成标准，不计入测试的行数也不能衡量鲁棒性。先实现一条完整可运行路径，再加功能；避免创建大量只会抛 NotImplementedError 的伪完成模块。

## 多 agent 分工

M0 的共享模型与实现由主 agent 负责，独立测试 agent 可在契约明确后编写 CLI 测试，reviewer 只读检查。锁定协议与流量接口后，再并行实施下表中的模块。共享文件包括 pyproject.toml、uv.lock、models.py、config.py、errors.py、app.py，只由主 agent 修改。

| 角色 | 允许修改 | 任务与产出 |
| --- | --- | --- |
| 协议 agent | protocol/、test_coding.py、test_protocol.py、协议 fixtures | 按原源码移植，给出向量与字节级差异说明 |
| 流量 agent | limiter.py、traffic.py、test_limiter.py、test_traffic.py | 对已固定接口实现流式下载、限速、目标冷却与取消 |
| 主 agent | 共享文件、http.py、auth.py、daemon.py、CLI、集成测试 | 做技术裁决、资源生命周期与集成 |
| 独立 reviewer | 只读 | 从需求和最终 diff 检查真实缺陷，给触发条件与证据 |

协议和流量两个任务并行即可；第三个实现 agent 仅在存在可独立验收任务时增加。auth 与 daemon 紧密耦合，初期由同一个人负责。不能把 agent 数量或投票数当作正确性证明。

使用独立 worktree 时，各 agent 从同一契约提交出发，依赖锁文件不各自修改，由主 agent 集成后统一验证。使用共享目录时严格限定写入文件，禁止互相 revert、批量格式化全仓库或重写公共接口。worktree 需要已经建立且有基线提交的 Git 仓库。

每个任务说明必须包含：目标、可写文件、接口与行为要求、禁止事项、验收命令。完成报告包含修改文件、实际运行的命令及退出码、未测试事项和已知风险。不能只说“测试全绿”，也不能靠删除失败测试达标。

reviewer 读取需求、当前代码和 diff，不必读取冗长设计争论；缺陷需有具体路径/位置、失败场景和修复建议。主 agent 将关键缺陷写成失败测试后修复，不必为每条意见再启动一个 agent。

## 必要测试

| 风险 | 验证方式 |
| --- | --- |
| Go 与 Python 算法差异 | 原 XEncode/SRBX1 向量；uint32 回绕、大小端、空输入、短 key、非 ASCII 字节 |
| 登录参数差异 | 固定 token/IP/ac_id/凭据，断言 info/chksum/MD5 与来源 fixture；登出不带密码 |
| 响应不可解析 | JSONP callback 校验、截断、错误页、非 JSON、小/超大响应、字段缺失 |
| 网络失败触发认证风暴 | 查询超时保持 UNKNOWN；同栈并发 ensure_online 只产生必要的一次登录 |
| 服务端已处理但客户端超时 | 登录返回超时后先复查，不能马上重复发登录 |
| 两栈相互影响 | v4 登录同时使 v6 在线；v6 请求失败但 v4 正常；错误密码阻断两栈 |
| 取消与未知异常 | 等令牌、读响应、退避时停止；故障任务触发有界退出，无遗留会话 |
| 总量和公平性 | 可控时钟测试预算公式；多个 worker 合计不因并发倍增，两栈都能取得预算 |
| 下载失败边界 | 200 忽略 Range、206 错范围、302 登录页、429 跨 worker 冷却、零字节、慢服务器；认证 Cookie 不进入下载会话 |
| 睡眠与恢复 | 大幅时间间隔后无积压请求或无限补发额度，旧请求不能覆盖新状态，保留账号阻断与冷却 |
| 明文配置风险 | JSON 类型/字段校验、写入中断旧文件完整、带凭据 URL 不出现在日志和异常输出 |
| 重复进程与退出 | 两进程争锁、进程异常退出后锁可恢复、只读 status 不被阻塞 |

纯单元测试使用假时钟与合成数据，不依赖公网。传输集成测试使用本机 aiohttp 测试服务；IPv6 回环不可用时只跳过相关测试并显示原因，不能宣称 IPv6 已验证。

速率测试分两层：确定性测试检查算法预算；本地服务器集成测试测长期平均值和合理偏差，计入冷启动与有限突发。不能用一次 sleep 后的单个测量断言网络级精确带宽。

CI 不访问 auth4/auth6，不使用真实账号，也不连续下载公共镜像。发布前由用户在校园网内运行一次双栈登录、查询、暂停网络后恢复、Ctrl+C 与显式登出测试，记录实际结果。

## 验证命令

M0 创建的包与 dev 依赖已支持以下命令。Windows 本次验证所用 uv 位于本地忽略目录 `.tools/bin/uv.exe`，未加入全局 PATH；安装了 uv 的环境可直接执行标准命令。

```powershell
uv sync --locked --group dev
uv run ruff check .
uv run ruff format --check .
uv run mypy src/thuauth
uv run pytest -q
```

日常修改先运行受影响测试，集成里程碑再运行全套。pytest 的退出码、跳过原因和失败信息都属于交付结果。安装受限或环境不可用时如实报告，不能用静态阅读代替“已测试”。

## Codex 使用方式

在 Codex 中打开 thuauth 仓库根目录，首先读取 AGENTS.md 和 HANDOFF.md。项目级长期规则放在 AGENTS.md，详细设计与当前进度分别维护，避免重复。Codex 对项目规则的读取方式见 [官方 AGENTS.md 说明](https://developers.openai.com/codex/guides/agents-md/)。本项目不固定个人模型、effort 或审批设置，也不把本机认证文件提交进仓库。

开始一个实施阶段可以直接使用下面的提示：

```text
请阅读 AGENTS.md、HANDOFF.md、docs/architecture.md、docs/development.md。
完成 M1，移植纯协议编码、登录登出参数与 JSONP 解析，并补齐 Go/Python 对拍。
先检查实际工作区状态，再按文档实施；关键设计冲突要指出。
不要连接校园网提交凭据，不要启动公网 bulk 下载。
对缺陷先写可复现测试；完成后实际运行受影响检查。
报告变更文件、命令和退出码，以及尚未验证的部分。
```

后续接口基线已具备、协议与流量任务可独立验收时使用（M0 完成不表示这些依赖已全部就绪）：

```text
以当前已提交的接口为基线，调用两个子 agent 并行实现协议与流量模块。
按 development.md 限定文件范围，并给每个 agent 明确验收条件。
主会话负责公共接口和集成。完成后交给只读 reviewer 检查故障路径。
独立运行集成测试，修复实际缺陷后提交结果，不用 agent 自评替代验证。
```

这两条提示分别适用于不同阶段，不要求每次修改都启动多个 agent。子 agent 的上下文继承、权限与隔离方式由实际工具决定；始终明确提供任务材料、可写路径与验收标准。用户已授权有限数量的子 agent 协作；当前环境不支持时改为串行，并如实说明。不要杜撰工具调用、后台任务或测试结果。可复用的完整任务模板见 [prompts.md](prompts.md)。

调试时提供复现命令、期望结果、实际输出和脱敏日志，要求先定位再修复。对涉及协议、取消或重试的 bug，至少补一个能复现缺陷的测试，不要求为纯文档或无行为格式调整补测试。

Codex 的模型、工具、权限与工作区隔离使用当前安装实际提供的能力。此前讨论中的 ultracode、Claude Workflow 或斜杠命令不属于本项目的前置条件。提高推理预算不代替实际验证。

里程碑完成后更新 HANDOFF.md 的实际进度、检查结果和下一步，再进行小范围 commit。新会话读取规则、交接文档与 git diff 即可接续，不依赖旧会话恢复。历史 Claude 规则和提示词已存于 [history/README.md](history/README.md)，仅用于追溯。

真实密码只由用户在本机交互或配置文件中输入。gitignore 不能撤回已提交内容，也不能覆盖所有自定义文件名；提交前检查暂存 diff。移植 GPLv3 代码时保留来源与许可证，依赖版本由 uv.lock 固定。
